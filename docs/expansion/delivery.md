# 测试、交叉审查与 commit 指南

配套：[目标路线](roadmap.md)、[64 项角色目录](roles.md)。本文约束每个阶段的实施和提交。

## 1. 规则先于实现

每个角色/变体先提供可审查的规则卡，再写实现。规则卡至少包括：

| 内容 | 必需说明 |
| --- | --- |
| 标识与依据 | 角色 ID、规则集/版本、来源和核验日期、中英文名 |
| 初始定义 | 身份、阵营、计数类别、本人知道的信息、胜利归属 |
| 信息与参与 | 互认、聊天成员、刀权、历史可见性、公开信息 |
| 动作 | 时点、目标、前置条件、是否可跳过、可重复次数 |
| 状态与资源 | 默认值、消费、生效/失效时间、复制/转移后的状态 |
| 交互 | 保护、反弹、封锁、毒、枪、决斗、殉情等判例 |
| 流程 | 遗言、警徽、死亡技能、追加死亡、判胜检查点 |
| 组合 | 至少一个支持板子、组合限制、未核验情况 |
| 文案与测试 | 中英提示/错误、人工预期、完整对局场景 |

发布稿只描述方向时，不能据此补猜精确数值或触发条件。临时选择 AWA 改编规则必须单独命名版本并说明与来源差异。

## 2. 测试分层

### T1 配置、目录和双语契约

- 64 项数量、唯一 ID、别名无冲突、实现状态与注册关系正确。
- 未实现角色/机制不可进入主动对局；注册缺失不能默认为好人或平民。
- 角色数量、座位引用、牌池、资源限制、locale、冲突机制和规则版本校验。
- 故意拼错字段、未知参数、不存在的角色/座位明确拒绝。
- 中英 key 与占位参数对齐，中文/英文都能构建规则摘要和当前支持角色提示。
- 翻译与展示切换不改变机器字段、动作、受众和胜负。

### T2 角色判例与业务不变量

每个新角色覆盖合法使用、不使用、错误目标、错误窗口、次数耗尽、生效/到期、死因、私有信息。人工预期来自规则卡，不调用被测函数计算“期望答案”。

共用不变量需要允许明确规则豁免：

1. 无效或重复提交不额外消费资源，不重复生效；已经结束的回合不能影响下一回合。
2. 合法动作接受与最终生效分别记录；受到保护、封锁等结果符合冻结规则。
3. 能力和资源变化都可解释到确定来源，角色/能力 ID 与状态一致。
4. 普通死亡玩家不能行动；死后动作必须存在本板要求的明确授权。
5. 牵连死亡按规则去重，死亡波次能终止，资源和技能次数不会形成无来源循环。
6. 终局后不再请求普通行动；规则要求的终局前连锁先完整结算。
7. 无权限玩家不得获知私有状态、未公布死亡、秘密投票或隐藏参与者。
8. 记录、最终状态、玩家投影、公开复盘和展示一致。

### T3 交互场景与组合覆盖

按机制覆盖，而非对 64 项角色做所有排列：

- 伤害来源 × 保护范围 × 受保护者状态。
- 死因 × 死亡技能资格 × 剩余次数。
- 能力复制/授予 × 资源继承 × 生效时间。
- 重定向/反弹 × 信息或攻击 × 目标身份。
- 投票修改 × 资格/票权 × 平票/终局临界。
- 阵营/关系变化 × 信息权限 × 获胜条件。
- 语言 × 规则提示 × 动作反馈 × 记录/展示。

为合法组合建立覆盖矩阵。成对覆盖用于普通组合；明确的三方及多方高风险场景必须手写，例如反弹＋附加查验＋咒狐、保护＋牵连＋末神死亡。未声明支持的组合不通过任意随机组牌绕过校验。

完整预期由规则卡及人工场景给出，不能直接重用生产伤害/判胜函数作为 oracle。每个曾出现的 bug 固定为最小回归案例。

### T4 可复现完整对局

#### 严格脚本玩家

运行真实 bootstrap、阶段管理器、网关、技能、结算、玩家投影和记录。只替换玩家决策。脚本以玩家、日次、阶段、该玩家回合序号匹配，不能假设并发请求全局顺序。

- 固定发牌和预期动作，意外多请求/缺请求、脚本未按预期消费直接失败。
- 校验事件顺序、重要状态、受众、最后结果和结束后的动作请求。
- 断言以稳定业务字段为主；时间戳、随机会话 ID 单独规范化，不依赖整份动态 JSON 快照。
- 阶段测试可直接准备状态，完整对局测试必须通过正常的阶段及结算流。

觉醒隐狼的首个完整场景应覆盖：模仿目标与身份信息 → 当夜新增能力尚未生效 → 后续获得实际行动机会 → 正确消耗复制能力资源 → 普通狼出局后的刀权 → 临界判胜与公开复盘。查验表现和是否可同夜执行多项能力以该版本规则卡为准，不能套用机械狼规则。

觉醒女巫的场景应覆盖：逐次选择不同数量协助者 → 只有授权协助者私聊/决策 → 全同意与有人拒绝两条分支 → 女巫能获知的反馈范围 → 重复协助限制 → 跨夜资源和死亡/取消边界。

#### 受限观察机器人

模拟玩家仅接受现有公共投影/提示策略生成的本人观察、合法工具和反馈，不持有 `World`、全部底牌、真实敌方阵营或上帝记录。测试控制器可以访问真状态来断言，不能把这项权限交给决策策略。

策略包括积极用技能、保守留技能、争警徽、随机合法行动、条件自爆/决斗、对允许信息的简单推理。可增加故意无效动作策略，单独验证拒绝和回退，不将其混入合法策略通过率。

模拟报告统计实际技能分支、跳过、拒绝和回退，而非只统计角色出现。保证每项限定技能及重要分支能由严格脚本场景触发，随机对局覆盖作为补充。

#### 随机源、时钟和失败录制

- 每局注入随机源，发牌/夜间顺序/每玩家策略使用可复现分流；并发完成顺序不决定随机数消费顺序。
- 并行游戏不改全局 `Math.random`。已做的隔离探索脚本不作为生产实现范式。
- 领域日志时间可规范化；超时和进程回收测试使用可控调度或合理容差，避免脆弱的毫秒级断言。
- 保存种子、规则/配置版本、归一化配置、发牌、动作请求/接受/生效序列、关键状态、事件和异常；同时保存引擎/构建或 commit 标识、RNG 算法版本及分流信息、录制 schema 版本和必要依赖锁版本。
- 回放先检查录制/规则/引擎/RNG 兼容性；不兼容时明确拒绝或运行有测试的显式转换。需要旧引擎时使用隔离环境，不覆盖当前工作区或凭据。
- 保存配置与日志时不包含 API key、认证文件内容、环境令牌等；公开导出仍按既定受众投影。
- 真实模型响应本身不确定；录制其实际行动用于离线复现，不要求“相同 seed 等于相同模型文本”。

#### 变更关系测试

- 只改变无权限私有信息时，玩家收到的信息保持符合授权；连同其系统/用户提示、允许动作、错误细节和可见序号一起检查。
- 在声明同步收集的阶段，响应延迟/完成顺序变化不改变票型与结果，不提前暴露别人的投票。
- 号码重命名的等价性只在规则没有按座位/编号裁决、邻接或策略依赖时断言；其他场景按明确映射验证，不能要求普遍不变。
- 切换 `zh-CN`/`en` 后，脚本行动对应的领域结果、受众及机器事件一致。

### T5 真接入通路、本地响应

使用实际安装的 SDK、真实 HTTP/SSE 或 ACP 子进程、ACP session 与注入 MCP。运行游戏流程而非只模拟阶段方法。

- 本地模拟服务提供动作/分片/无工具/错误参数/过期回合/重复调用等行为。
- 测试多步工具、结构化拒绝、纠正后重试、响应尾部、取消、超时、迟到响应、进程退出与 MCP 回收。
- 冻结并测试 provider/单局/玩家的并发作用域及排队、初始化、重试的预算；覆盖排队取消/超时、迟到 session、不能正常退出的强制回收。结束后断言租约/等待队列/pending turn、子进程/进程组及 MCP 监听资源均释放；运行错误与清理错误分别保留。
- LLM 与 ACP 游戏/审计两条工具通路分别断言 `zh-CN`/`en` 的工具及参数说明、静态 schema 查询和拒绝文案；sidecar 语言随当前任务传递，工具名/key/enum/回合 ID 与业务结果不变。
- ACP 仅授予当前对局或审计任务注入且获授权的对应工具；游戏和审计会话分别限于自己的 bridge/server，禁止跨任务授权，其他权限请求不能因测试便利一并放行。
- 两条接入应给出一致业务接受/拒绝效果，资源消费和最终状态一致。
- 正常模拟接入预期零非预期回退；故障用例明确预期回退次数与理由，防止回退掩盖接入失败。
- 测试工作区和端口彼此隔离，不读宿主机真实认证，不访问外部模型。

### T6 小规模真实模型评测

使用授权的 Agent 和隔离配置，限制局数、时长、重试和花费。作为发布评测，不能因为随机模型文本变化阻塞所有提交。

观察合法行动率、技能理解、资源使用、错误回退、私有信息泄露、对不同规则的推理、胜率趋势、人格和欢乐发言。语言分别测试；真实原始发言按原文保留。不能用单局文本完全相等或短期胜率必须 50% 作硬门槛。

严重规则错误、信息泄露、失控花费/进程保留属于阻断项；策略平衡与欢乐度用样本评测和趋势判断。失败对局转化为离线脚本，规则部分进入确定性回归。

## 3. 每个阶段的验收运行

数量为起始建议，可依耗时和风险调整，但需要在提交说明中解释：

| 时机 | 运行内容 |
| --- | --- |
| 开发中 | 修改涉及的判例、角色交互、完整场景及 locale 检查 |
| 功能提交前 | 类型/边界检查＋受影响板子 20–50 个固定种子＋涉及的真实接入本地测试 |
| 阶段结束 | 所有已支持角色/板子回归、双语和公开复盘/前端测试 |
| 定时回归 | 每支持板子约 1000 个种子、分支覆盖、非法动作/并发扰动场景 |
| 发布候选 | 必要构建/E2E、长局资源与记录验证；各主要接入/重点新板子 1–3 局真实模型，设置预算 |

不按 64 项角色任意全排列。先维护“声明支持板子矩阵”，再增加经核验的组合；检查器拒绝没有支持资格的组合。

当前已有命令（项目根目录）：

```bash
bun run --cwd backend release:check
bun run check:frontend
bun run test:frontend
bun run build:frontend
bun run --cwd frontend test:e2e
```

未来的目录/i18n/模拟/录制检查入口由各阶段建立并加入实际 scripts；文档中不能把尚不存在的命令写成可用验收入口。浏览器、网络、进程监听或真实模型所需环境受限时，记录未运行的门槛及原因，不宣称已通过。

P0 仅文档：检查目录计数、唯一 ID、中英文标签、阶段引用、相对链接、审查记录及 `git diff --check` 即可，不运行无关模型对局。

## 4. 子代理交叉审查安排

### 4.1 审查角色

| 审查职责 | 内容 |
| --- | --- |
| R 规则与范围 | 名单遗漏/重复、版本来源、阵营/能力/刀权、死因/判胜、声明支持板子 |
| A 架构与运行时 | 模块职责、状态唯一所有者、类型与配置、SDK/ACP、超时/取消/回收、并行隔离 |
| T 测试与信息权限 | 人工 oracle、脚本/随机整局、交互覆盖、私有信息、失败复现及回退统计 |
| L i18n 与数据/呈现 | 双语语义与覆盖、稳定 ID、旧复盘迁移、前端/终端/视频、玩家原文 |
| D 交付与迁移 | 依赖/步骤、commit 可回退、样例迁移、当前与目标状态、阶段门槛 |

职责可以合并到同一代理，但每阶段至少两名独立审查者；高风险阶段至少覆盖三组职责。最多三个子代理并行，其余审查分轮完成。根代理负责整合，不让审查者相互写同一批文件。

### 4.2 各阶段审查矩阵

| 阶段 | 第一轮子代理 | 交叉复查重点 |
| --- | --- | --- |
| P0 文档 | R；A+T；L+D 三路 | 全量范围/版本、测试与停止边界、双语和提交步骤；修订后由原审查者复查 |
| P1 配置 | R+D；A；L+T | 严格 schema/交叉检查、角色规则卡、迁移及 locale/敏感字段 |
| P2 测试底座 | A；T；R | 按局 RNG、脚本严格性、机器人的观察权限、独立预期及完整记录 |
| P3 i18n | L；A+D；T | 多局语言隔离、机器数据中性、旧复盘、英文提示/界面与视频 |
| P4 公共基础 | A；R；T+L | 业务接收与执行、能力/死因/胜利结构、并发和取消、错误双语 |
| P5 第一批 | R；T；A+L | 死亡动作、决斗/自爆中断、警徽/遗言/判胜、双语与通路 |
| P6 第二批 | R；T；A+L | 互认/夜聊/刀权、邻接、牵连/保护和历史信息权限 |
| P7 第三批 | R；A；T+L | 复制/赠予资源及调度、查验、胜利归属、隐狼权限与会话状态 |
| P8 第四批 | R；T；A+L | 多人目标、情侣/第三方、辩论/重投、事件/道具受众和改编规则 |
| P9 扩展包 | R；A；T+L，每波次重复 | 多人秘密决策、多次技能、替死、反弹/吞噬、延迟死亡等特有交互 |
| P10 总体验收 | R+D；A+T；L | 64 项状态与测试、支持矩阵、长局/并行/回放、双语全链路 |

如果实现委派给子代理，至少一名审查者不能是该实现的作者。高风险问题修正后，原提出者复查，并由另一职责的审查者检查修改引入的交互影响。

### 4.3 审查输入与输出

审查任务须提供目标阶段、具体文件/commit 范围、规则卡、相关配置、测试结果、明确未决事项；默认只读，不提交或写代码。独立审查完成后再共享意见，减少先入为主。

输出格式：严重程度、文件/位置、具体问题、复现或规则证据、影响、修正建议。允许发现“缺少足够来源无法决定规则”，不要求审查者猜答案。

维护审查记录：首轮意见 → 根代理处理 → 原审查者复查 → 最终状态。只由根代理判定阶段完成；子代理“未发现问题”不等于测试已经执行。

- 阻断项：规则错误、授权信息泄露、数据/资源丢失、重复生效、不能复现、主动配置静默忽略、支持范围双语缺失、旧复盘损坏。
- 阶段提交前关闭阻断项及影响本阶段正确性的高优先级问题。
- 其他问题说明是否处理、理由和后续阶段；不得把未通过目标默认为完成。
- 无充分证据的规则争议回到规则卡冻结；架构选择由根代理结合已授权范围作决定，避免无限互相否决。

## 5. Commit 拆分指南

### 5.1 通用原则

1. 每笔围绕一个可解释、可验证的功能边界，保持仓库可构建、可运行并可回退。
2. 纯迁移/重命名与行为修改分开；迁移中的必要 import 修正可在同笔完成。
3. 某功能的实现、相关测试、必要 schema/双语文案和样例一起提交，避免“只登记角色但不能运行”的半成品。
4. 公共基础、独立角色、跨角色判例、板子配置按依赖拆分；同一角色如必须多笔，先交付禁用/不可选择的内部基础，启用提交包含完整门槛。
5. 测试底座单独提交；角色特有的正常/异常/交互测试跟随角色实现。
6. 每个可公开选择角色的启用提交必须具备中英文与完整场景，不能先上线中文再补英文。
7. 提交消息写实际功能；正文说明行为、原因、规则版本、验证和审查、迁移或限制。
8. 不提交 `configs/` 中认证、机器绝对路径、真实对局私有资料或下载的整份外部手册。可提交无认证的 `configs.example/`、人工合成测试 fixture 和来源链接。
9. 既有用户授权持续有效；阶段 scope 改变需显式记录。本轮 P0 完成后的等待边界是用户要求，不得自动开始 P1。

### 5.2 建议提交序列

以下是拆分模板，不要求未来固定 commit 数量；每阶段根据实际改动继续拆小：

| Commit | 阶段 | 一笔的边界 |

### 5.3 每笔提交前检查

- `git diff --check`，检查范围只含本功能和必要依赖。
- 运行受影响门槛；达到阶段边界时运行阶段完整回归。
- 确认中英文案与公开数据变化，更新规则卡、目录状态和示例。
- 交叉审查问题已按要求关闭，复查者知道最后的 diff。
- 说明没有执行的必要门槛；不能把跳过的真实模型评测算通过。
- 本地 commit 后确认工作区状态，向用户报告 commit、功能、验证、审查及剩余阶段。

## 6. 规划维护

代码实现与用户接受的范围发生变化时更新路线、角色状态、支持矩阵及审查记录。新的角色或机制提议先进入候选并写清依赖；不能将候选直接登记为已支持。

文档首笔提交完成后停止。后续依用户指令继续，从 P1 的契约和规则冻结开始，不自动写生产代码、升级依赖或运行真实模型。
