# AWA 玩法扩充目标与实施路线

- 规划日期：2026-10-07。
- 状态：实施目标，未上线的角色和配置不得按当前功能对外说明。
- P0 边界：文档与首笔文档 commit 已完成；用户于 2026-10-07 授权开始完整实现，进度见 [progress.md](progress.md)。
- 配套文档：[角色目录](roles.md)、[测试、交叉审查与 commit 指南](delivery.md)。

## 1. 完成目标

1. 在现有多夜狼人杀流程中逐批支持 **64 项角色定义**：现有 7 项基础角色、新增 57 项。角色名单与计划 ID 以 [roles.md](roles.md) 为准。
2. 支持明确版本的板子、角色变体、信息权限、技能时序、多人交互、伤害与死亡连锁、阵营和个人胜利目标。
3. LLM、ACP、模拟玩家共用玩家观察信息和动作接收规则；保持各接入方式的会话、传输与资源生命周期职责。
4. 提供可复现的完整对局测试、真实接入通路测试、复盘一致性验证和失败案例回放。
5. 首先支持简体中文 `zh-CN` 与英文 `en`，覆盖前端、终端、规则和 Agent 提示、错误说明、审计摘要及复盘展示。
6. 各阶段经过独立子代理交叉审查，修正问题后按功能提交，保留可定位和可回退的历史。

### 1.1 总体目标与交付批次

64 项是本次已约定总目标，不是全世界所有狼人杀角色、全部已发布角色或完整觉醒系列，也不代表已经核验全部版本。前四批角色的原交付顺序保留；依赖更复杂基础能力的角色安排到后续扩展阶段。每项都必须具有确定的规则卡与测试才能标记完成。

完整验收包括：角色可配置、技能真正进入阶段流程、AI 得到正确提示及工具、权限与规则校验正确、结果可记录和回放、中文和英文可用。仅加入枚举、名字、提示词或默认机器人分支不算完成。

## 2. 当前事实与修改理由

以下是规划开始时的代码事实，后续实现时应重新核对：

- `GameBoard` / `BoardName`、配置解析和解析后选择仅接受六人、十二人两个内置板子名。
- 板子同时接受平铺、结构化和多板子覆盖形式；部分未知字段会被静默忽略。探索验证中 `roles.wolf_king` 解析为空覆盖，`voteWeigth` 拼写错误未被拒绝。
- 对局 Agent 引用会校验，但 `roleAgents.wlof` 和 `playerAgents["99"]` 尚未结合板子交叉校验。
- `RoleProfile` 已集中注册初始化、技能、阶段、校验、修复与死亡钩子；这项分工可以复用。
- 玩家提示按 `Camp.Wolf` 给出狼队友，夜聊按 `Role.Wolf` 收集参与者；特殊狼牌需要分别表达信息、夜聊和刀权。
- 死亡钩子及网关还直接使用猎人开枪专用接口；查验主要是二值结果，伤害主要是四种印记。
- `GameResult` 当前主要返回获胜阵营；个人或关系组胜利需要更完整结果。
- LLM 接收动作时已有参数修复及部分状态校验，ACP 接收主要检查回合和工具名；新技能之前需要统一业务接收结果。
- 当前中文文字散布于后端注册表、提示模板、错误、终端和前端。`PlayerRoundRecorder` 还把本地化阶段名称写入记录，前端日期格式固定 `zh-CN`。
- 基线机器人可读取全局身份，烟测为六人局。2026-10-07 的隔离探索脚本在六人、十二人各运行 100 个固定种子，均自然结束；十二人局用药、自爆覆盖均为 0，开枪覆盖 57 局、白痴翻牌覆盖 23 局。这证明需要主动覆盖分支，不能只看结束率。该探索不是新的 CI 测试套件。

已实现行为以代码与测试为准；本文约束后续目标、交付与验收。

## 3. 架构职责

### 3.1 继续使用的模块

- `RoleCatalog` / `RoleProfile`：角色定义、规则与能力装配。
- 夜间阶段注册：已注册机制收集、去重及明确排序。
- `ToolGateway`：实际执行前的输入清理和业务校验。
- `PhaseManager`：阶段推进、规则集要求的判胜检查点及终局。
- `DeathResolution`：死亡波次、死亡动作及追加死亡结算。
- 玩家可见性投影、`PlayerPromptPolicy`：玩家输入与提示词。
- recording / audit / replay-contract：记录、审计与公开复盘格式。

规则行为用 TypeScript 实现并注册，配置负责选择角色、规则版本和参数。保持 LLM 与 ACP 的组合式装配；不为角色扩充增加统一 Agent 基类、事件总线、事件溯源、配置脚本语言或通用投票引擎。

### 3.2 必须明确的业务边界

1. **角色身份、阵营、能力集合、胜利归属分别表达。** 技能复制不自动改变阵营；新增能力不覆盖原身份。
2. **狼队信息、夜聊、刀权分别表达。** 互认可以是双向、单向、部分或无；接刀规则独立于查验标签。
3. **稳定玩家 ID 与座位/号码映射分别表达。** 换号码、换技能目标、换底牌是不同规则，不能共用含混的“交换”动作。
4. **提交、合法接受、实际生效分别记录。** 因保护而未致死的合法攻击，应有清楚反馈；无效提交不消耗资源或关闭合法行动窗口。
5. **死因、伤害来源、保护范围、追加死亡和判胜点有明确语义。** 结算顺序来自冻结的规则集，阶段管理器拥有推进与最终判胜。
6. **玩家信息按事件发生时的授权投影。** 新加入夜聊或改变阵营不应自动得到此前无权查看的历史；是否补发历史必须有本板规则。
7. **Agent、名字与人格跟随玩家。** 角色/能力变化通过可见状态更新通知；不能因此丢弃对局历史或擅自更换模型。
8. **每局状态独立。** 随机源、locale、规则和能力状态不使用可被并行对局覆盖的进程级可变单例。

## 4. 配置目标

### 4.1 文件职责

| 文件区域                 | 负责内容                                                    |
| ------------------------ | ----------------------------------------------------------- |
| `runtime/providers.json` | 模型服务、ACP 进程、传输与认证引用                          |
| `runtime/agents.json`    | Agent 装配、模型参数、会话策略及默认提示                    |
| `boards/<id>.json`       | 人数、身份组合、规则集/版本、角色及机制参数                 |
| `games/<name>.json`      | 板子引用、座位/昵称/人格/Agent 绑定、locale、seed、运行限制 |
| 可选人格/事件/道具资料   | 可复用的已校验定义与中英文内容，不包含可执行代码            |

允许 Agent 继承对局默认值，使更换整局模型不需要改写每个人格。角色绑定、座位绑定及提示词覆盖/继承语义需在 P1 冻结；保留目前“显式提示词整体覆盖”的行为，叠加必须有新的明确配置，不能静默改变已有对局。

### 4.2 配置校验要求

- 板子 ID 按合法标识读取对应文件；未知 ID、缺少文件、注册缺失明确报错。
- 统一板子公开格式，明确配置格式版本和规则语义版本；二者用途不同。
- 角色参数由角色定义贡献 schema、默认值与语义校验；主动配置中未知角色、变体、字段均拒绝。
- 在完整板子合并后检查人数与牌数、座位范围、角色引用、数量限制、依赖能力和冲突机制。
- 无该角色却提供参数、无警长却提供警徽配置等情况应明确告知，不能悄悄丢弃。P1 定义哪些拒绝、哪些显式警告。
- 保留 typed actions/events 和配置类型，注册检验不能退化为任意字符串和未校验对象。
- 新增只读配置检查入口，展示最终参数及字段来源，输出时屏蔽认证、令牌和敏感环境值。
- 随机种子、规则版本、归一化板子及玩家绑定进入可复现记录；凭据不进入记录。
- 录制同时保存引擎版本/构建或 commit 标识、RNG 算法/版本与分流方式、录制格式版本；回放明确拒绝不兼容版本或运行显式转换，不仅依赖 seed。
- `configs.example/` 与命令示例同步迁移。旧格式保留范围、明确转换与移除节点必须在 P1 写明，避免长期扩张多层隐式回退。
- 提供实际使用的本地忽略配置迁移说明及备份办法；默认不覆写用户凭据、人格或游戏偏好。

本文提到的未来字段或 ID 尚不能直接写入当前配置使用；P1 的契约 commit 冻结确切格式。

### 5.2 并发、预算与资源门槛

P1 冻结配置命名与默认语义，P4 实现并验收：

- 明确限额属于 provider、单局还是玩家；同一 provider 的多角色共用限额，跨进程使用同一密钥的叠加不能被声明成全局受控。
- 定义排队、初始化、工具循环和重试是否计入同一回合截止时间；原则上使用一个回合 deadline，并受全局截止时间约束，不在重试后重新获得完整预算。
- 排队期间超时/取消能移除等待者，不能之后抢到租约再启动过期回合；初始化迟到、prompt 迟到和阶段切换后的提交明确丢弃/回收。
- 关闭先尝试有界正常取消与退出，必要时强制回收；验收本局租约、等待队列、pending turn、子进程/进程组和 MCP 监听资源都已释放。
- 同时发生运行与清理错误时分别保留；清理不能覆盖原始错误。

## 6. 中文与英文 i18n 要求

### 6.1 语言与数据边界

- 第一版支持 `zh-CN`、`en`，缺省 `zh-CN`；显式未知 locale 在配置检查时拒绝。
- 对局 locale 决定规则提示和公共玩家语言；终端/播放器的展示语言可独立切换，缺省跟随对局。
- 审计系统生成说明和摘要使用指定展示语言。语言切换不得改写历史发言、模型原始思考、用户名或原始动作。
- 角色、阵营、phase、stage、事件、动作、错误、原因和规则 ID 均为稳定机器值。工具名、JSON key、`turn_id`、数字与资源状态不本地化。
- 记录使用稳定 ID 和结构化参数；文案只在呈现或提示构建时生成。保留当时的提示和玩家文本用于复现，但不把它们当业务主键。
- locale 随每局/每个展示上下文传递，不用全局可变语言开关。
- ACP 游戏及审计 MCP sidecar/session 显式得到 locale 上下文，并与当前对局/任务一致；语言不能因子进程缺省配置回到中文，也不能扩大其环境或文件授权。

### 6.2 覆盖范围

1. 64 项角色与所有支持变体的名称、技能说明、阶段指令、合法目标提示和规则摘要。
2. 共享系统/用户提示、动作错误及重试说明、初始化和取消相关的人类可读提示。
   同时覆盖 SDK 工具/参数的 `description`、游戏/审计 MCP 工具说明，以及 `get_game_schema`、`get_audit_schema` 返回的固定说明。工具名、参数 key 和 enum 值保持机器契约不变。
3. 终端事件、Agent 观察输出的系统标签、CLI 错误与配置检查报告。
4. 审计任务的系统规则与生成摘要，固定规则类问题的原因说明。
5. 前端按钮、筛选、加载错误、事件时间线、席位、阶段、胜利结果及空状态。
6. Remotion 画面及视频渲染入口；locale 属于显式渲染输入，同 frame 和输入得到同样画面。
7. 运行时间/时区/数字展示使用显式 locale 与展示设置。
8. 内置人格的中英文语气及示例内容；自定义字符串保留原文，不自动机器翻译。多语言人格缺少所选语言时，检查工具明确报告回退到哪个版本。

### 6.3 实现约束

- 共用角色/阶段/事件术语目录与稳定翻译 key；模块可以贡献文案，前端仅依赖共享契约/本地化资料，不导入后端引擎。
- 允许保留现有注册表接口进行分批迁移；不维护前后端两份独立角色词典。
- 中文与英文语义一致，使用占位参数与完整句子模板，避免拼接中文词序生成英文。
- 英文角色标签在角色目录中是工作译名；不得因同名就与海外不同规则角色建立别名。
- 支持范围内缺少 key、占位参数不一致、无意中文硬编码由 CI 拒绝。检查采用受控扫描/目录校验和运行测试；玩家文字、示例数据等有明确例外，不使用“禁止一切汉字”的粗糙规则。
- 正常版本不依赖回退掩盖缺翻译；历史或外部未知角色/事件可安全显示稳定 ID 或双语未知提示，不能影响主动配置的严格拒绝策略。
- P3 处理已有记录里本地化的 phase/stage：明确新公开复盘版本、旧版本转换及 fixture。不能无说明地重命名已保存字段，不能靠模糊猜词恢复机器状态。
- 翻译修改不改动作合法性、事件受众、资源和判胜。更换语言后，领域结果及机器事件序列应一致。
