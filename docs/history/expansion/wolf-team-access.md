# P4 G01：狼队知识、夜聊与刀权

当前 P6 的[隐狼](hidden-wolf.md)与[石像鬼](gargoyle.md)已通过各自规则控制互认/夜聊/刀权；下文 G01 子批的未启用表述是历史范围。

## 明确权限

`RoleProfile.wolfTeam`声明狼队能力；`Camp.Wolf`只说明阵营，不授予身份知识、夜聊或刀权。未声明权限、未注册profile和非狼阵营均无这三项权利。普通狼profile声明双向pack互认、夜聊和刀权，基础七项的注册/支持状态不增加。

| 字段 / 查询                           | 契约                                                                                            |
| ------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `recognizedByPack`                    | 是否出现在具有pack互认权限的其他狼的队友名单中                                                  |
| `recognizes`                          | `pack`只认识公开给狼队的成员；`all`认识所有狼阵营；`none`不获显式队友名单；role数组表达部分互认 |
| `canChat` / `wolfChatParticipants`    | 独立的夜聊参与权，实际参与者还必须存活                                                          |
| `canVoteForKill` / `wolfKnifeHolders` | 独立的狼刀投票权，实际投票者还必须存活                                                          |
| `knownWolfTeammates`                  | 逐viewer查询、排序、排除本人；不使用未公开的存活状态删掉已知队友                                |

互认名单与聊天并非匿名协议：即使recognizes=none，若canChat=true，仍可看到已授权战术顺序和发言者ID，不能把无显式名单宣称为无身份推断。

权限也可由profile纯函数读取该角色的私有状态返回。状态初始化、授予/复制、接刀条件与触发时点由后续角色/能力机制拥有；G01不把“其他狼都死了”等假设硬编码成统一继承规则。部分互认、无夜聊的刀权、单向互认通过合成profile判例验证，未提前登记隐狼/石像鬼等目标角色为实现。

共同PlayerPromptPolicy的系统提示、每轮行动提示与受限观察DTO共用上述查询，SDK/ACP不分别按Camp重新推导队友。系统提示记录会话建立时的知识，每轮共享user提示提供当轮授权名单；缓存system不能遮蔽新增/撤销授权，旧知识仍属历史事实。公开板子构成从传入boardConfig复制；兼容未传板子的调用在policy构造时捕获开局构成，不能用当前隐藏身份重新计算角色数量。中途构造policy的调用者必须提供公开板子，不能把中途真实牌面当作公开输入。NightStageRegistry和校验注册表分别把其实际RoleCatalog传给阶段/规则，不引入另一套全局权限注册表。SDK/ACP provider的可选roleCatalog同时进入提示、接收规则与默认Baseline；低层SdkGameToolLoop可显式接收同一规则注册表，AcpTurnRegistry第三参数接收目录，旧省略参数仍使用默认目录。默认Baseline的狼聊/刀票也重新检查当时权限、夜间和存活；显式自定fallback仍由最终网关约束。

## 调度与执行

普通狼夜聊沿用逐夜随机顺序、三轮与本人end_chat规则；普通狼刀票沿用原夜聊顺序。刀权收集独立于夜聊名单：具有刀权且未夜聊的角色按稳定ID追加。刀权名单在该阶段开始时收集，开始请求/每次重试/接受后均重新核对当前资格；在该动作最终校验/生效前死亡或撤权不产生有效票、补弃票或继续模型重试。已生效的刀票仍是当时事实，后来撤权不会倒扣；需要撤销既存票的特殊机制应单独冻结。在阶段开始前生效的授予可参与当夜刀票；异步决策中途的新授予不会另开并行窗口。

接收预检与最终网关使用相同profile权限；狼聊/刀票必须在夜间执行。四个新稳定拒绝code具有中英说明：`wolf_chat_permission`、`wolf_kill_permission`、`wolf_chat_phase`、`wolf_kill_phase`。接收成功仍是accepted/applied=false，执行时撤权可以使原选择不生效。普通狼自爆仍沿用独立规则；窗口、死因/警徽差异随G03修正。

## 事件发生时授权

四种狼队事件的内部GameEvent有必填只读`audience`：战术顺序、夜聊、结束夜聊、狼刀票。发出时复制并冻结排序去重的玩家ID数组；前三区取当时存活夜聊参与者，狼刀票取当时存活夜聊参与者与刀权者的并集。`end_chat`只结束本人的发言，不撤销其接收本夜后续夜聊的权限。

投影和延迟落盘均只按保存的audience读取：后来进入狼队不能追溯读取旧狼聊；死亡、换阵营或撤权不能删去曾经被授权的历史事件，未来事件则按未来的参与资格记录。通用custom可见性规则不能扩大这四类事件已冻结的受众。无audience的历史/手工狼队事件默认不可见，不按当前阵营补猜。

`audience`不进入PlayerVisibleEvent、玩家私有event DTO、公开`replay.json`或前端/视频格式；玩家seq仍按可见事件连续递增。`replay.json`原有`perspective: god`的观战内容没有被改为玩家视角，仍保留其既有狼聊事实。受众只进入内部动作Tape，必须与重建引擎事件完全一致。

## 录制兼容与验证

Tape使用独立RecordedGameEvent序列化envelope，reader不把旧档冒充audience必填的领域GameEvent；Trace的输入仍必须是领域事件。内部schema已随G04升2，旧1拒版；RecordedGameEvent envelope的audience在结构中可选，实际授权狼队事件必写；数组只接受严格递增、正整数、最多128项，且只可用于上述四类事件。当前引擎生产者始终写入该字段；重放对缺失/篡改受众拒绝。source/lock/规则版本核对未放宽，旧引擎Tape不会被按新权限静默重放。公开/私有播放器schema仍为2，历史原文保持。

人工判例覆盖：普通/单向/部分互认、无权限狼阵营、未公开死亡不泄露、夜聊但无刀/有刀但无夜聊、阶段拒绝、授予后调度、请求期间撤权、历史受众不漂移、延迟玩家落盘、隐藏seq以及受众不进入wire/观战文件。真实合成本机SDK HTTP与MCP验证四个新拒绝两语言一致且仍可更正；既有六/十二人完整模拟、双语SDK/ACP/混合对局与严格Tape继续回归。

具体特殊狼的查验标签、互认版本与接刀时点仍由P6/P7规则卡冻结；能力查验/资源、死亡结算与胜利基础已分别交付G02–G04，见[阶段验收](reviews/p4-activation.md)。没有引入事件总线或事件溯源。
