# 严格 Tape3：保存被拒的返回候选

基于 `e8837e9f`。八个真实混血儿失败场景暴露记录缺口：Provider 正常返回 null 后，领域三次拒绝均只留下 error；重放把第一条当成 Provider 抛错，后两次请求没有开启，最终因果死锁。

本笔将内部严格 Tape 升为 3，只在实际 false 结算时保存此前安全复制的 `returnedCandidate`。outcome 仍为 error；候选不证明接受、付款或撤销。真 Provider 抛错与交付检查早拒不产生该字段。重放只重交明确记录的候选，两个关系校验器仍以最后已知回复约束前缀。公共复盘／玩家内层维持 2，manifest 维持 1；旧 Tape2 保原严格读取且拒绝新字段，精确构建检查保留。

## 实际验证与审查

- 新增回归先在旧实现红：后端 4 通过、5 失败；共享包 1 通过、2 失败。修补后分别 9 通过／69 断言与 3 通过／15 断言。
- 版本写入合同 11 通过／59 断言，具体迟到前缀 4 通过／1,770 断言。
- 原八场景的正面精确重放保留并通过。末尾负例改为既有独立审计层的准确错误，最终 8 通过／249 断言；伪造回退许可仍被拒绝。
- 首次类型检查仅两个新测试辨别不充分；修正后仅重验这两声明，2 通过／16 断言。最终 15 个修改源／测试根的真实传递图零诊断，不冒完整类型项目通过。
- 两路非作者独审分别核核心与共享格式，再绑定实际输入和日志。所有修改文本二次格式化稳定；关键字段、所有权和失败边界使用中文说明。
