## 原生行动与 AWA 时序

1. **夜初冻结**实际存活、原生命与侍女是否为末狼。普通狼不知道侍女身份，侍女从初始化知道狼队；本板无身份变化，已知身份不会因死亡丢失。末狼资格只取真实夜初，夜中死亡不能补发刀权。
2. **侍女吞噬**：第二夜起可以明确跳过，或选择一个当前存活的好人。不得选上一真实夜吞噬的同一号码；中间明确跳过打断连续。它已知本板全部狼人，合法目标列表不增加未知阵营信息。确认后快照原生能力状态并暂时封禁原主；不给侍女原主既往查验结果、梦境全部历史或提示笔记。
3. **庇护**：原生伯爵未被吞噬时行动；吞伯爵的侍女用借得的庇护行动。第二夜起可明确跳过，或选择一个其他存活玩家，连续限制取上一真实夜。借用时不能自保的“自己”指侍女。不能先执行伯爵再吞噬后回滚已发生动作。
4. **反噬事实**：吞了伯爵本人或本夜最终受庇护对象时，标记侍女的独立夜间反噬伤害。吞噬仍成功、原主仍封禁、已借能力仍可使用；不立即杀死侍女，不提前告知反噬是否成立。
5. **其余夜阶段**：正常梦、狼聊、狼刀、药和查验按照现有有名阶段推进。侍女在相应阶段使用借得技能；若它夜初已经是末狼，同夜还可进行一次普通狼刀，但始终没有普通狼聊或自爆权限。
6. **统一夜末**：先确定保护、独立伤害与梦连锁；临时封禁在本夜行动关闭后到期，借得的使用授权关闭。夜死仍统一公布、死亡链完成后再判胜。未存活的原主不会因“恢复技能”被复活。

临时封禁与借用由本板单一夜租约拥有者关闭，不能只依赖 `expiresAfterDay`（同夜序的白天仍未超过该日期）。正常夜末关闭与异常中止分开：吞噬后借用请求失败、取消或 jumpTo 时，撤销借用授权并解除暂时封禁，但保留已经提交的吞噬、借用消耗和攻击证据。记录独立的上帝可见关闭事实，明确 `committed` 或 `aborted`；中止不发布正常恢复通知、夜死或胜利，也不代表本夜正常完成。失败前缀最终快照反映授权已关闭、原主未被永久封禁，角色库存按已提交行为保留；同夜不能重领租约或重新执行借用。解除封禁只作用于租约捕获的原角色、原生能力实例和原生命；实例或生命已替换时只关闭租约，不按同一 playerId 启用新实例，也不覆盖其他禁用原因。解除封禁不要求原主仍存活，但绝不复活。正常关闭后仍待处理的已提交保护与梦关系有独立原生命绑定，不能用已关闭的授权句柄继续判定它们是否存在。

首夜双方没有新增技能请求。合法跳过与传输缺失、非法响应、取消、迟到严格分开；新增技能、被接管技能及本板规定必答狼聊／狼刀失败保存失败前缀。此要求不改普通发言、选举、投票的既有缺失策略。

## 当前状态与资源的 AWA 裁定

官方资料没有明确借用后是否写回原主库存，本版本采用**独立快照、不写回**，公共规则和双方角色提示必须直述，不隐藏在实现中：

| 吞噬对象 | 当夜获得             | 资源与历史                                                                           |
| -------- | -------------------- | ------------------------------------------------------------------------------------ |
| 村民     | 无主动技能           | 吞噬记录保留，原角色不变，不产生假工具回合                                           |
| 预言家   | 一次当夜正常查验     | 只得到当前可用能力，不复制旧查验结果；新结果只给侍女                                 |
| 女巫     | 当时尚存的解药／毒药 | 已耗药不刷新；借药只消耗借得库存，原主库存不变；隔夜再次吞噬重新快照当时库存         |
| 摄梦人   | 当夜摄梦             | 继承上一目标及夜序用于连续梦判定；当夜施法者及死亡牵连主体是侍女；结果不写回原主历史 |
| 流光伯爵 | 当夜庇护             | 继承上一目标及夜序用于禁止连续；借用行为不写回原主；反噬单独保留                     |

借得空药时没有额外的强制 none 回合：仍记录成功吞噬及空库存，但不发借用药动作请求；这不改原生女巫既有的空药流程。快照按能力白名单构造：药只带当前库存及本板药规则，当夜使用标志从 false 开始；梦只带 lastTarget、lastDay 和保护政策，历史数组为空；庇护只带所需连续限制状态；查验不带历史或上次结果。不能通过复制整个 state 后再筛显示来满足隐私。

借药每夜最多一瓶，禁止自救；只有借得解药尚可用时才见当夜普通狼刀原目标。选择合法用药即消费，不按隐藏保护或最终是否存活返回不同错误。伯爵庇护与解药同中不产生守卫式“同守同救”；本板没有守卫。

原摄梦人／伯爵被封禁的夜间没有原生行动，也不虚构一次 pass 去修改其上一目标日期。到下一夜时，是否连续按真实日期判定。借来的梦同样不能选择侍女自己。临时借用结束后，其已合法提交的当夜保护、伤害和梦连锁事实仍完成结算，不能随着能力句柄失效被抹掉。

## 伤害与人工判例

反噬使用独立机器死因，来源为 Night；天亮公布不能把它误归 Day。保护过滤与连锁须分别验证：

1. 原伯爵护 A，普通刀／毒 A：A 存活；药和刀选择仍有真实记录。
2. 伯爵护 A，A 连续被梦或梦主夜死：本板庇护阻止对 A 的对应梦伤，不留下虚假 `dream_death`。
3. 侍女吞伯爵后庇护狼人免毒：庇护有效，侍女另因反噬死亡，不能倒销保护。
4. 伯爵护预言家、侍女吞预言家：原预言家无行动，侍女得到自己的查验结果，并独立触发反噬。
5. 原摄梦人梦侍女且存活：梦保护抵消反噬。原梦主同时死亡：反噬可被挡，但侍女仍被梦牵连。
6. 侍女连续两夜被梦且触发反噬：保护不免除连续梦的独立致死。不能因为“反噬被挡”就删除所有死因。
7. 女巫剩双药／单药／空药被吞：手写借得库存及原主次夜库存；使用后再隔夜吞噬不能从角色默认值重新发满药。
8. 原梦主 N1 梦 A、N2 被吞；侍女 N2 梦 A按继承状态造成连续梦。N3 原主恢复，其上次原生行动仍是 N1，不把侍女的 N2 行动写回。
9. 前夜最后普通狼死亡，侍女本夜继承刀权；同夜才发生的死亡不补刀。刀、借用技能、反噬可同夜并存。
10. 区分攻击提案与有效死因：侍女被梦保护，同时受到反噬与毒，梦主实际死亡，则反噬和毒已被过滤，最终仅剩梦牵连，不能把三种攻击都写入有效死因。多个实际有效来源仍只处理一次死亡／遗言／警徽；最后一狼等整条死亡链后统一判胜。
11. 原女巫 `(heal=1, poison=0)`，N2 侍女借救使用后，借库存为 `(0,0)`、原主仍 `(1,0)`；N3 原主不用药，N4 再借为 `(1,0)`。若 N3 原主用了解药，N4 再借为 `(0,0)`，没有借药请求。
12. 原女巫双药，N2 侍女借毒；N3 原主不用药，N4 再借仍为双药，这是从原主重新快照的合法结果。若 N3 原主用毒，N4 只借得解药，不能沿用侍女旧实例或重新套默认值。
13. 原梦主 D 被吞、侍女 M 梦 A：D 当夜被普通刀杀、M 活，A 不因 D 牵连；M 当夜被毒杀，A 获得 M 为施法者的梦牵连。借用句柄已关闭也不能取消已提交的梦关系。
14. 伯爵庇护梦主 D，D 受到普通刀、A 为 D 的梦目标：D 获得保护存活，不能因此前提议伤害把 A 追加进 linked 或记录虚假梦死。
15. N1 D 梦 A，N2 侍女吞 D 并梦 A，伯爵护 A 令其存活；N3 D 再梦 A，不连续致死，因为原生 lastDay 仍为 N1。
16. 伯爵 N2 护 A，N3 被吞，由侍女护 B；N4 原伯爵护 B 合法，不把借用者 N3 的选择写回。
17. 侍女借庇护保护原梦主、梦主梦侍女；普通刀打梦主、毒与反噬打侍女，双方存活，无虚假梦死。

## 信息、实现与验收

- AWA 信息裁定：被吞者仅获知自己当夜原生技能受封禁及恢复；不知道侍女号码、借用实例 ID、她用了什么或查了谁。侍女知道吞噬目标角色及必要当前能力状态，不获得历史私密内容或隐藏庇护／反噬原因。
- 原生与借得行动使用不同且稳定的能力标识。夜、生命、施法者／目标身份、库存、借用实例或阶段在 await 前后变化即撤销旧授权，不能换同号码继续执行。
- 先实现有限状态、原生能力封禁与当夜借用，再接庇护/反噬/梦交互；保持既有能力组合方式，不建立统一 Agent 或复制所有角色的通用框架。
- 隐私负例改变原主旧 history、lastResult、uses 和 lastUsedDay，保持允许的当前库存及必要上一目标字段相同；侍女的 SDK/ACP system、当前提示、事件和工具错误不得出现历史 canary。借用实例的 uses 与 lastUsedDay 从新实例初值开始，不能带出原主使用次数；只有梦／庇护判连续所需的上一夜日期可进入其白名单状态。
- 独立 Tape 按手写资源和伤害矩阵审计初始状态、每项请求资格、借用到期、原主恢复、事件受众及每个 checkpoint；拒绝刷新库存、写回原主历史、抹反噬、伪造保护及提前死亡。
- 双语规则摘要必须覆盖完整公共版本；实际 SDK/ACP/混合通路覆盖正常、失败和长局，受限观察机器人运行固定种子。前端/终端/Remotion 区分私有选择与真正死亡，逐帧回退和最终 checkpoint 一致。
- R、A、T/L/D 至少三组交叉审查，修正后由原审查者复核；功能提交与集中门禁遵守[维护指南](../guides/add-mechanism.md)。未经实际验收不改变角色 implemented 状态。
